DownloadProgressTracker 

object DownloadProgressTracker

Byte counts for the download currently in flight, readable from outside the JVM.

A Spark driver launched through py4j writes to a stdout that a notebook front end does not surface, so DownloadProgress's own output is invisible there however it is formatted. Python can print to the notebook, but has no view of the transfer -- it is blocked in a py4j call for its whole duration. This is the bridge: the JVM keeps the counters, and the Python side polls them and renders.

Every download on the driver shares this one set of counters. Two downloads at once (a job that builds several pipelines on threads) therefore mix their numbers in the display, which is cosmetic: each download's own data is unaffected. Accessors are plain public methods returning primitives, which is what py4j can reach.

  20.  def setRenderedByCaller(value: Boolean): Unit

    Set by Python around a download it draws itself, so this JVM does not draw a second copy onto the same terminal.

    Set by Python around a download it draws itself, so this JVM does not draw a second copy onto the same terminal. pyspark starts the JVM with a piped stdin, so the JVM never has a console and would otherwise print one line per percent even in a terminal. Counted rather than a flag: two notebook cells downloading at once each set it, and the JVM stays quiet until both have cleared it.

  22.  def snapshotWithGeneration: String

    snapshot behind a number that every new download increments, as generation|active|done|total|label.

    snapshot behind a number that every new download increments, as generation|active|done|total|label. Python notes it when a download call starts, so it can tell that call's download from counters an earlier one left behind (even a download that starts and finishes between two polls) and can follow a second download in one call. A separate method rather than a wider snapshot, so older Python keeps parsing that.
